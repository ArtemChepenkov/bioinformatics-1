# Визуализация пайплайна и её отличия от блок-схемы алгоритма

## Как получена визуализация (использованный способ)

У GNU make нет встроенной команды «нарисовать граф», но есть машинно-читаемый
**вывод внутренней базы зависимостей** в режиме трассировки. Цепочка такая:

```bash
make -Bnd -f pipeline/Makefile all 2>/dev/null \   # 1. дамп дерева зависимостей
  | python3 scripts/make2dot.py                     # 2. -> граф Graphviz (DOT)
  > results/dag.dot
dot -Tsvg results/dag.dot -o results/dag.svg        # 3. рендеринг
dot -Tpng results/dag.dot -o results/dag.png
```

Всё это завёрнуто в цель `make -f pipeline/Makefile dag`.

1. **`make -Bnd all`** — make обходит весь граф зависимостей и печатает отладочные
   строки:
   * `-n` (dry-run) — ничего не выполнять, только разобрать зависимости;
   * `-B` — считать все цели устаревшими, чтобы в обход попали *все* рёбра;
   * `-d` — отладочный вывод с фразами `Considering target file 'X'.`,
     `Pruning file 'X'.`, `Finished prerequisites of target file 'X'.`.
2. **`scripts/make2dot.py`** — разбирает этот вывод стековым алгоритмом (как
   утилита `makefile2graph`): вложенность `Considering … / Finished …` задаёт
   связь «цель ← её зависимость», а `Pruning file` восстанавливает рёбра к уже
   рассмотренным целям. На выходе — граф на языке DOT, где ребро направлено
   `зависимость → цель` (поток данных от входов к выходам). Узлы раскрашены:
   жёлтые — входные данные, синие — промежуточные файлы, красные — финальные
   выходы (VCF, маркер FINISHED), зелёный овал — `.PHONY`-цель `all`.
3. **`dot`** (Graphviz) — раскладывает DAG сверху вниз и рендерит в SVG/PNG.

Источник графа — **сама база зависимостей make**, а не нарисованная вручную
схема. То есть это автоматическая визуализация фактического пайплайна: если
изменить `Makefile`, картинка перестроится из его реальных зависимостей.

Результат: [`results/dag.svg`](../results/dag.svg), `results/dag.png`,
исходник графа — `results/dag.dot`.

## Полученный DAG

```
ref/ecoli.fa ──> ref/ecoli.fa.bwt ─┐        reads/sample_1.fastq.gz ─┐
ref/ecoli.fa ──> ref/ecoli.fa.fai  │                                 ├─> fastqc/.done ─┐
                                   └────────reads/sample_{1,2}──┬─────> sample.sam      │
                                                                       │                │
                              sample.sam ─> sample.bam ─> sample.flagstat.txt           │
                                                │                  │                    │
                                                │            sample.mapped_pct.txt      │
                                                │                  │                    │
                                                │            sample.qc_status.txt       │
                                                │                  │                     
                                                └──────────> sample.sorted.bam <─────────┘(qc_status)
                                  ref/ecoli.fa.fai ──────────────> sample.vcf
                                              sample.vcf, fastqc/.done ─> sample.FINISHED ─> all
```

## Отличия DAG (make) от блок-схемы алгоритма

Блок-схема в задании — это **схема потока управления** (flowchart): порядок
*действий* во времени, с ветвлением-ромбом «%mapped > 90 %?» и двумя исходами
(OK / not OK). DAG из make — это **граф зависимостей данных между файлами**.
Отличия:

| Признак | Блок-схема алгоритма | DAG из GNU make |
|---|---|---|
| Что узел | действие/операция (FastQC, bwa mem, «Parse %mapped») | файл-цель/артефакт (`sample.bam`, `sample.vcf`) |
| Что ребро | переход к следующему шагу (порядок выполнения) | отношение «зависит от» (что из чего строится) |
| Ветвление | есть ромб-решение с двумя ветками (OK / not OK) | **нет** — make декларативен, не имеет if/else в графе |
| Циклы/повторы | возможны (стрелки назад) | запрещены: это *ацикличный* граф (DAG) |
| Параллелизм | не выражен явно | виден: независимые ветки (FastQC ∥ картирование) идут параллельно (`make -j`) |
| Направление | сверху вниз по времени | от входов (данные) к выходам (результаты) |
| Терминальные «Write OK / not OK / Finished» | отдельные блоки-действия | не отдельные узлы графа, а *логика внутри рецепта* QC-gate |

Главное концептуальное различие — **ветвление-решение**. В блок-схеме узел
«%mapped > 90 %?» имеет два выхода. В DAG-зависимостях такого узла-развилки
быть не может: граф лишь фиксирует, что `sample.sorted.bam` зависит от
`sample.qc_status.txt`. Само решение OK / not OK реализовано не структурой
графа, а **рецептом** цели `qc_status`: скрипт сравнивает процент с порогом и
при недоборе завершается с ошибкой (`exit 1`), из-за чего make не запускает
зависящие шаги (sort → freebayes). То есть «ромб» блок-схемы превращается в
make в *условие внутри шага + обрыв ветви по ошибке*, а не в отдельную вершину.

Кроме того, в DAG появляются узлы, которых нет в блок-схеме, но которые
реально нужны как зависимости: индексы референса (`ecoli.fa.bwt`,
`ecoli.fa.fai`) и служебный маркер завершения (`sample.FINISHED`). И наоборот,
последовательные «технические» действия блок-схемы (например, «Rename and save
QC-report») в DAG растворяются внутри рецептов соответствующих целей.
